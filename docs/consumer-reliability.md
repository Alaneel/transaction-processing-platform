# Consumer reliability

The transfer activity projection reads `TransferCompleted` records from Kafka. It writes no balances or ledger entries. PostgreSQL remains the authority for transfer correctness, and the projection can lag while transfers continue committing. `GET /api/accounts/{id}/activity` returns its paired debit/credit activity for a user account, with event identity, transfer identity, occurrence time and projection time. It is explicitly eventually consistent.

## Durable processing boundary

`EventProcessor` decodes UTF-8 bytes and validates the supported event envelope before opening a transaction. It requires a matching immutable local outbox event and compares the decoded payload with that committed origin. An otherwise well-formed event with a forged identity, changed amount or impossible transfer is permanently invalid.

The transaction inserts `event_inbox`, one `transfer_activity_projection` row and two `account_activity` rows. An inbox primary key arbitrates concurrent deliveries of the same event. A transfer uniqueness constraint prevents a second logical identity for that transfer. The stored SHA-256 digest covers canonical serialization; matching duplicate deliveries return `DUPLICATE` and apply no additional activity. Unique constraints serialize competing transactions, so a competing delivery can proceed if the first rolls back.

Database insert guards verify that projection identity, accounts, amount and occurrence time describe the completed transfer. A deferred constraint requires the inbox, transfer projection and exactly two activity rows to commit together. Update, delete and truncate guards protect processed history. These protections apply to the runtime database role; a privileged administrator who disables protections can invalidate them.

The guarantee is one successful projection effect per logical event within this PostgreSQL boundary. Kafka records and processing attempts may be duplicated. An offset commit is a separate Kafka operation and is never represented as atomic with PostgreSQL.

## Offsets, ordering and rebalance

`EventConsumerWorker` owns one raw Kafka consumer on one background thread. Automatic offset commits are disabled. `max.poll.records=1` limits business work to one delivery. The worker calls `commitSync` with that record's partition and `offset + 1` only after its inbox/projection transaction or quarantine transaction commits. It never commits a later offset for an unprocessed record. Kafka offset gaps are harmless: committing the next position can cause a redundant poll across a gap but cannot skip an unprocessed record.

Restart begins at Kafka's committed offset; `auto.offset.reset=earliest` applies when no retained committed offset exists. A crash before the DB commit leaves no partial projection. A crash after that commit can cause redelivery, which the durable inbox recognizes. An ambiguous offset acknowledgement causes a retry and can increase duplicate-attempt counts without changing the projection.

Rebalance callbacks commit nothing. Revocation clears any in-memory pending reference for that partition. PostgreSQL effects already committed remain deduplicable if another member receives the record. Stopping the worker immediately fences subsequent offset acknowledgements and wakes Kafka polling. A test paused inside a fault seam must release its latch before a terminated worker can restart; `isTerminated()` verifies the old thread has exited.

Processing preserves Kafka delivery order within each partition in a worker; it provides no global or cross-account order. Multiple workers can process different partitions concurrently. The projection records source occurrence time and receipt time so clients can choose presentation order. Long-lived keyset pagination is a view of an evolving projection: refresh from the beginning to discover records that were still in flight during an earlier page.

Phase 3's asynchronous relay does not add financial or per-account publication ordering. Producers key records by transfer identity, and concurrent claimers, retries and callback/settlement timing can reorder distinct events before Kafka appends them. Partition append order cannot restore their original transfer order. The implemented projection appends one paired activity effect per independent terminal transfer; it does not apply a versioned account state or derive spendable balances from receipt order. Its inbox identity and origin checks therefore tolerate distinct-event reordering. A future stateful aggregate projection would need explicit version/order handling before adopting this assumption.

The implementation follows Kafka's distinction between fetched position and committed position. See the [Kafka 4.3 consumer API](https://kafka.apache.org/43/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html) for manual commits, consumer liveness and rebalance semantics.

## Retry and backpressure

Before polling, the worker constructs its Kafka client. Construction retries only when the exception or one of its causes is a `ConfigException` whose message is exactly `No resolvable bootstrap urls given in bootstrap.servers`. This recognizes Kafka 4.3.1's bootstrap-address resolution failure even when wrapped in `KafkaException`. Other configuration errors and unrecognized construction failures stop the worker and require inspection, correction and an explicit worker/application restart. The recognized condition uses the same capped exponential backoff with jitter and increments `events.consumer.startup.retries` once per failed construction attempt. It retries while the worker is active; a persistent hostname typo can produce the same condition as a temporary DNS outage. See Kafka's [bootstrap address validation](https://github.com/apache/kafka/blob/4.3.1/clients/src/main/java/org/apache/kafka/clients/ClientUtils.java).

Startup retries have no fetched record, projection effect or offset acknowledgement. Their delay checks the stop flag at intervals of at most 100 ms. Kafka cleans up partially initialized client resources when construction fails; a successfully constructed client is owned by the worker's try-with-resources block. Stopping also fences a client that finishes constructing after the stop request. The three-second stop join is a bounded wait, not a guaranteed termination deadline: synchronous JVM/operating-system DNS resolution during construction is outside Kafka API timeouts, and both it and client cleanup can outlast the join. `isTerminated()` checks actual thread exit, and starting a replacement worker is rejected while the old thread remains alive. Kafka's [consumer implementation](https://github.com/apache/kafka/blob/4.3.1/clients/src/main/java/org/apache/kafka/clients/consumer/internals/ClassicKafkaConsumer.java) and [consumer API](https://kafka.apache.org/43/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html) describe initialization cleanup and close behavior.

Transient PostgreSQL connection failures, transaction timeouts, lock conflicts and recoverable Kafka failures retain the pending record. Database transactions have a configurable timeout plus local statement timeout and a 500 ms lock timeout; pool acquisition and Kafka API waits are separately bounded. Exponential backoff uses jitter between half the capped delay and the capped delay. A pending record is retried indefinitely while the dependency recovers, because a transient failure is not evidence that the event is invalid.

Consumer retry delay and the current delivery's attempt count are process-local and reset on restart/reassignment. Eligibility survives through the unadvanced Kafka committed offset, while inbox/quarantine identities and replay audits remain durable. The stored quarantine processing-attempt count reflects the delivery that created its evidence, not a lifetime cross-restart retry total. Relay next-attempt scheduling and claim counts are persisted separately in the outbox.

The worker pauses delivery and continues polling during backoff to service heartbeats and rebalance callbacks. If a rebalance assigns a partition inside that poll, any newly returned record is sought back to its original offset. This matters: silently discarding such a record would advance the fetched position and allow a later commit to skip its side effect.

There is one application-held pending delivery. Kafka fetch buffers are bounded by configured partition and aggregate fetch sizes, subject to Kafka's first oversized-batch exception and the broker's record/batch limits. No executor queue accumulates unprocessed records. When consumption is slower than publication, Kafka carries the backlog. `consumer-min-interval-ms` adds an optional bounded delay for reproducible backpressure experiments; its default is zero.

An unexpected application or invariant error stops the worker, retaining the unacknowledged record for inspection and restart. Injected `EventFaults.Crash` always stops the worker and never quarantines the record. If PostgreSQL cannot persist a quarantine record, that record also remains unacknowledged. This dependency outage can pause progress, which is necessary to preserve evidence.

## PostgreSQL quarantine

Malformed JSON, unsupported schema/type, invalid UTF-8, absent payloads, invalid fields, oversized payloads and impossible local origins are permanent failures. They immediately enter `event_quarantine`. Only after its DB commit succeeds can Kafka's offset advance, allowing subsequent records to proceed. There is no secondary Kafka DLQ publish that could be lost after an offset commit.

The unique key `(consumer_group, topic, partition, offset)` makes quarantine insertion safe after a crash between quarantine commit and offset acknowledgement. Evidence includes the best recoverable original event identity, original key, exact raw payload bytes, SHA-256, original byte length, classification, safe bounded error code/message, attempts and timestamps. For values exceeding one MiB, the stored prefix is explicitly marked truncated and the full value's hash and byte length remain inspectable. Replay then requires a corrected complete payload. Original evidence cannot be overwritten.

Inspection endpoints:

- `GET /internal/quarantine?after=0&limit=50` lists a bounded page, ordered by ID.
- `GET /internal/quarantine/{id}` exposes exact base64 bytes and a UTF-8 display representation. Base64 is authoritative for invalid UTF-8.
- `GET /internal/quarantine/{id}/replays` shows the ordered audit trail.

The internal API has the same local trusted-operator assumption as the Phase 1 internal endpoints. Authentication and authorization remain an explicit deployment prerequisite, outside this project's current scope.

## Controlled replay

`POST /internal/quarantine/{id}/replays` accepts `{ "reason": "operator explanation", "correctedPayload": "optional complete JSON text" }`. The reason must be nonblank and at most 500 characters. Corrected payloads are capped at one MiB. A row lock reserves an incremented replay attempt and commits a `STARTED` audit before execution. The configurable per-record budget defaults to five; the next attempt after that limit returns HTTP 409.

An original recoverable event identity must remain unchanged after correction. When the original bytes have no recoverable identity, an operator-supplied valid correction explicitly adopts its local outbox identity, recorded in the replay audit. Replay applies the same contract/origin validation and the same inbox/projection processor as ordinary consumption. It does not publish a new Kafka event and does not rewrite the original quarantine evidence.

Successful replay commits its projection effect and terminal audit result together; replay of a previously processed logical event records `DUPLICATE`. Permanently invalid replay records `REJECTED`. A transient dependency failure or process interruption leaves `STARTED`, indicating an uncertain/interrupted attempt that consumed a budget slot. Operators inspect it and issue another bounded replay if appropriate; a later retry deduplicates any committed effect. No unknown outcome is labeled definitely failed.

## Reconciliation and metrics

`GET /internal/events/reconciliation` uses one repeatable-read snapshot. It reports completed transfers, processed events, projection rows, completed transfers awaiting projection, published events awaiting processing, missing inbox/projection links, malformed paired activity and origin mismatches. Normal delivery lag is reported separately from structural discrepancies. It exposes the oldest unprocessed event age, the latest stored inbox processing timestamp and the latest processed occurrence time.

Metrics include consumer processing duration and outcome throughput, retries by bounded dependency class, duplicate/quarantined outcome counts, offset commit failures, rebalance transitions, Kafka maximum record lag where available and worker running state. Projection gauges include processed/pending counts, discrepancies, oldest unprocessed age and last processing epoch. They refresh from one bounded five-second snapshot, with snapshot age exposed so stale metrics are visible. Propagation duration measures transfer occurrence to projection processing; HTTP response latency is a separate measurement.

The pipeline instrumentation separates these observations without changing the one-record processing or manual-offset policy:

| Metric | Observation and bounded labels |
| --- | --- |
| `events.consumer.ingestion.records` | Counter incremented when a normal poll's record becomes the pending delivery. Retrying that held delivery does not increment it; Kafka redelivery does. Records returned during paused heartbeat polling and sought back are counted only when later admitted for processing. |
| `events.consumer.poll.duration` | Normal Kafka poll duration, including an idle wait, with `outcome=empty\|received\|failure`. Heartbeat polling is included in pause duration instead. |
| `events.consumer.processing.duration` | Existing timer around one processor invocation, including decoding, projection or quarantine, post-commit fault seam and logging. It excludes polling, offset acknowledgement and configured delay; controlled replay does not invoke this wrapper. |
| `events.consumer.database.transaction.duration` | Monotonic elapsed time from immediately before `TransactionTemplate.execute` until its return/exception, including connection acquisition, transaction setup, callback work, commit or rollback, and cleanup. Labels are `operation` and `result=committed\|failed`. |
| `events.consumer.database.work.duration` | Nested callback duration, including SQL, timeout setup and the before-commit fault seam. Records only when the callback starts, with `result=completed\|failed`. |
| `events.consumer.database.completion.duration` | Nested time from a normally completed callback until the transaction returns/throws: commit/deferred constraints plus transaction cleanup. A failed callback has no completion sample. Labels are `operation` and `result=committed\|failed`. |
| `events.projection.commits` | Counter after a successful projection transaction returns, before the after-commit fault seam, with `source=kafka\|replay` and `outcome=processed\|duplicate`. A duplicate commit applies no new activity. |
| `events.consumer.offset.acknowledgement.duration` | One explicit `commitSync` attempt, after the durable outcome and before-offset fault seam, with `outcome=success\|failure`. Timer count gives acknowledgement attempt throughput. A failure can have an uncertain broker outcome; the retained inbox still permits safe retry. |
| `events.consumer.pause.duration` | Actual elapsed startup delay or paused heartbeat backoff, with `reason=startup_retry\|retry\|optional_delay`. It includes early shutdown and excludes processor execution. |
| `events.consumer.paused` | One while the worker is inside one of those delays, zero outside them. Startup delay has no constructed consumer; connected delays pause delivery and poll for group liveness. |

Database `operation` is restricted to `projection`, `quarantine`, `replay_reserve`, `replay_projection` and `replay_reject`. All three database timers record after transaction exit. Their intervals are nested: do not add work/completion duration to total transaction duration, or add the transaction timer to the containing processing timer. Completion is an observed client interval around commit and cleanup, not an isolated JDBC commit call or a PostgreSQL WAL timestamp. A failed transaction sample includes rollback or an uncertain commit failure; it does not prove that the server rolled back.

For live Kafka projection throughput, use the fixed-window change in `events.projection.commits{source=kafka,outcome=processed}` divided by elapsed time. Inspect duplicate commits separately. The existing `events.consumer.outcomes` counter also includes controlled replay and records after the after-commit fault seam, so its total is not an independent ingestion count. Process-local counters can reset on restart or miss a process death between database commit and metric recording; persisted inbox/projection counts and reconciliation remain the completeness evidence. Backlog drain throughput uses the scoped backlog and its drain interval, which differs from a sustained input window.

`events.consumer.startup.retries` counts recognized construction failures separately from delivery retries. `events.consumer.running` reports the worker's active lifecycle flag: it stays at one during startup retry and does not establish a broker connection, group assignment or processing progress. It becomes zero when stopping is requested, even if the thread is still finishing cleanup. Use pending age, processing freshness, retries and available lag alongside it to assess progress.

Stored `processed_at`/`projected_at` values are captured inside the successful transaction and become visible only after commit. They are not PostgreSQL WAL commit timestamps. SQL propagation quantiles use those capture times; the post-transaction Micrometer propagation timer includes the remaining commit work. Neither should be confused with client HTTP latency.

An increasing pending count and oldest age suggests delivery or consumption is falling behind. A stopped consumer, sustained retries, any structural discrepancy, rising quarantine outcomes or a stale metrics snapshot warrants inspection. Event/transfer/correlation IDs appear in log context, never metric labels. A maximum Kafka lag value alone is not a complete consumer-group lag measurement; it is available for the locally assigned consumer and needs broker/group-level inspection for whole-group operations.

The [Phase 3 methodology](phase3-benchmark-methodology.md) checks broker committed offsets against log end separately after SQL drain. The consumer's local lag gauge concerns fetched position, so zero reported fetch lag does not prove the final DB effect or offset acknowledgement. [Backlog admission](backpressure.md) can use published-without-inbox pressure to restrict new transfer keys when enabled; it does not commit offsets, discard retained records or alter duplicate/quarantine semantics.

## Phase 3 consumer decision

The separate [optimized stage diagnostic](benchmarks/phase3-profile/optimized-stage-analysis.json) offered 500 scheduled requests/s for eight seconds with eight clients. It completed 3,934 requests, shed 66 locally and reported no HTTP errors or invariant failures. All scoped events were published at input end, while 949 published events awaited processing. SQL observations measured processing at 363.1/s during concurrent HTTP input. Projection transactions averaged 2.080 ms, offset acknowledgements 0.432 ms and received polls 0.106 ms. Nested SQL work and completion/cleanup accounted for about 1.479 and 0.592 ms respectively; these overlapping observations are not an additive capacity model.

After input stopped, the fresh drain-start snapshot retained 813 events. They processed at 610.7/s over 1.331 seconds; projection transactions averaged 0.897 ms and offset acknowledgements 0.171 ms. The difference points to shared PostgreSQL/application resource contention during HTTP work, rather than an exclusively offset or poll bottleneck. The short catchup interval is not sustained capacity. This diagnostic is separate from the matched comparison and proves that 500/s still accumulates consumer pressure in this tested schedule.

Keep the sequential consumer and explicit per-record commit policy for this phase. The relay removes the measured publication limitation without introducing parallel offset/rebalance coordination. Both optimized thirty-second trials at 500 scheduled arrivals/s accumulated consumer backlog, whereas both separately declared 250/s trials matched creation, publication and processing at about 245 accepted events/s and had no input-end backlog. Their propagation p99 was 304–314 ms. This is a short local operating point, not a maximum rate or long-duration capacity guarantee. Future consumer work should measure transaction/commit cost under concurrent input, then compare bounded partition/group scaling or SQL improvements with the same correctness gates. See the [complete performance report](phase3-performance.md) for repeated results and limitations.

Inbox, projection, quarantine and replay history are retained indefinitely in this version. Retention must preserve deduplication for the entire possible Kafka replay horizon and preserve operator evidence; deleting inbox identities alone can enable duplicate effects. Current immutable-history guards deliberately prevent casual cleanup. Large history makes reconciliation scans more expensive and requires a designed archive/retention strategy before long-term deployment.

At 178,795 retained events, a global reconciliation observation failed when a parallel PostgreSQL query could not allocate a 16 MiB shared-memory segment inside the container's 64 MiB shared-memory budget. Later unchanged-environment HTTP/SQL reconciliation and committed-offset checks confirmed complete effects. The [inspection evidence](benchmarks/phase3-sustainable-250/gate-stop-inspection.json) retains that operational failure; zero scoped backlog does not establish that global inspection remains available at arbitrary history size.
