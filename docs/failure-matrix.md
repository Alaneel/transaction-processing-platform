## Error classification and recovery ownership

Before client construction succeeds, only a causal `ConfigException` whose message is exactly `No resolvable bootstrap urls given in bootstrap.servers` is retried. Each recognized attempt increments `events.consumer.startup.retries` and uses capped exponential backoff with jitter; other construction/configuration errors stop the worker. Persistent bad hostnames can match the retryable condition and require operator inspection. There is no fetched record or offset to acknowledge during this phase. `events.consumer.running` denotes the worker's active lifecycle flag, including startup retries, and does not establish broker connectivity or processing freshness. A stop request sets it to zero before cleanup necessarily completes; actual termination is inspected separately.

Permanent envelope or semantic errors immediately use durable quarantine. Transient consumer database/connection/lock failures retain the record and back off while servicing group liveness. A failed/uncertain offset commit may already have succeeded in Kafka; replaying the effect is safe through the inbox. Unexpected invariant/programming errors stop the worker and retain the unacknowledged record for inspection.

The relay conservatively records delivery/network/status-write uncertainty as AMBIGUOUS and retries. A missing acknowledgement does not prove that Kafka rejected the record. Expired claims remain eligible for recovery, including when a failed status update cannot reach PostgreSQL. Known permanent event/topic/authorization failures remain BLOCKED until audited requeue. Neither path deletes history after an arbitrary retry count.

A PostgreSQL quarantine commit precedes offset advancement. Failure to persist evidence leaves the record unacknowledged; it can pause the group during a DB outage. A crash after quarantine commit can repeat quarantine insertion, whose unique group/topic/partition/offset key preserves one evidence row. Replay never creates a new logical projection identity merely to bypass the inbox.

## Invariants and test bounds

Every pipeline test checks that completed transfers have one outbox event, no event belongs to an uncompleted transfer, PROCESSING is not durable, journals have exactly two zero-sum postings, balances match their ledger sums, every inbox has its projection and paired activity, and authoritative reconciliation remains consistent. Per-event checks compare projected accounts, amount, unit and occurrence time with the completed transfer. Fault cases inspect the state at the failure boundary before eventual success.

The harness uses real PostgreSQL 17.11 and Kafka 4.3.1 containers. Each scenario creates a separate random database, topic and group; independently wired application contexts use separate pools. Kafka evidence is read independently of the production consumer, and AdminClient inspects committed offsets/group membership. Polling assertions and per-test execution have bounded deadlines. Cleanup closes apps, drops only the scenario's randomly named database and stops suite-owned containers; no unrelated Docker resource is pruned.

Tests simulate application boundary crashes through injectable seams, real broker stop/restart, real DB contention and actual consumer group handoff. They do not simulate power loss, kernel failure, disk corruption, a multi-broker cluster, PostgreSQL failover or arbitrary long network partitions. Broker acknowledgement guarantees depend on the configured replica/ISR/storage assumptions. Privileged owners can bypass schema guards. Kafka retention loss and automatic rebuilding remain untested/unimplemented limits.

The verified database guarantee is logical exactly-once activity within its inbox transaction. Kafka transport, application attempts, acknowledgements and external business effects do not share a universal exactly-once guarantee.
