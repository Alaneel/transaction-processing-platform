# Portfolio walkthrough: measured event-pipeline optimization

This project demonstrates how to improve an asynchronous pipeline while preserving a transactional ledger. It uses fictional integer units and one modular Java application. The engineering story is the sequence of evidence, a bounded change, and failure recovery—not a claim of production financial readiness.

## Start with the financial boundary

The completed Phase 1 snapshot is `2fd2543`; its financial model remains the authority. [TransferService](../src/main/java/dev/tpp/application/TransferService.java) arbitrates an idempotency key through PostgreSQL, locks account rows in deterministic order, and commits balances, balanced postings, and terminal transfer state together. Phase 2 adds one immutable outbox event in that same transaction. Kafka network calls stay outside it, and activity projection never determines balances. Explain this boundary using the [architecture](architecture.md) and [ledger invariants](ledger-and-invariants.md).

An identical prior key recovers the committed result; a changed payload conflicts. A broker acknowledgement does not make an uncommitted financial transaction successful. Financial history, event identity, consumer effects, and Kafka offsets have distinct durable boundaries.

Its original diagnostic drained 2,986 scoped events in 25.674 seconds, approximately **116.3 events/s**. Timer observations showed **19.330 seconds of explicit polling pause**, or **75.4% of batch-plus-pause time**. Per-event renewal and published-status transactions consumed another **4.204 seconds** inside active batch work. Mean Kafka acknowledgement time was about 0.423 ms. The consumer mostly waited for publication.

Use the [raw report](benchmarks/phase3-baseline-diagnostic.json), [stage analysis](benchmarks/phase3-baseline-stage-analysis.json), and [image/environment provenance](benchmarks/phase3-baseline-provenance.json). Nested timers overlap: full batch time includes SQL/send work, and callback acknowledgement overlaps the coordinator’s wait. Adding every timer would misstate the cost.

The original fixed-arrival fixture also exposed ten insufficient-funds responses when reordered or shed directions depleted an unfunded reverse source. The [audit](benchmarks/phase3-baseline-diagnostic-fixture-audit.json) remains visible; matched fixtures fund both sides. The original 116.3/s observation diagnoses stages and is excluded from the matched comparison because its drain boundary differed. This is useful evidence of investigation discipline, not an inconvenient result to erase.

## Walk through the bounded change

[OutboxRelay](../src/main/java/dev/tpp/events/relay/OutboxRelay.java) has one coordinator and a reusable producer. It claims a bounded batch, renews live generations together, submits asynchronously, freezes results at one deadline, and settles them in one bounded database transaction. A fully successful batch immediately continues; idle, partial, and failed work retains the configured pause and durable retry scheduling.

[PublicationBatch](../src/main/java/dev/tpp/events/relay/PublicationBatch.java) maps each result to the immutable event ID and claim token. It creates the slot before sending because a callback can arrive before `send` returns. A valid acknowledgement requires the expected topic and a nonnegative partition/offset. A frozen result cannot be reopened by a late callback. A record semaphore remains occupied until that actual producer call completes, even when its coordinator times out, so repeated timeouts cannot create unbounded outstanding sends. Callbacks perform no SQL or fault-hook work.

[OutboxStore](../src/main/java/dev/tpp/events/relay/OutboxStore.java) fences each status update with event ID, token, `CLAIMED` state, and a live lease. It returns applied IDs only after transaction completion. Publication success metrics follow that committed result. Read [ADR 009](adr/009-bounded-batch-relay.md) and the [outbox algorithm](outbox.md) for the exact resource and shutdown limits, including producer construction outside Kafka API timeout guarantees.

## Explain the uncomfortable failure cases

A stale worker can still append to Kafka; fencing protects PostgreSQL status, not the network. A crash after broker acceptance or an uncertain status commit can therefore produce duplicate records. One settlement failure also rolls back the entire status transaction, leaving acknowledged members eligible for recovery rather than inventing partial durable success.

The [consumer processor](../src/main/java/dev/tpp/events/consumer/EventProcessor.java) checks the immutable origin, canonical payload digest, and inbox identity. It commits the inbox, transfer projection, and two account activity rows atomically. Offset acknowledgement follows that commit. Redelivery deduplicates the logical effect; poison data instead commits quarantine evidence before its offset is acknowledged. This is at-least-once delivery with idempotent database effects, not universal exactly-once processing. The [failure matrix](failure-matrix.md), [batch state tests](../src/test/java/dev/tpp/events/PublicationBatchTest.java), and [real PostgreSQL/Kafka scenarios](../src/test/java/dev/tpp/events/EventPipelineTest.java) make these boundaries reviewable.

## Discuss overload without promising a hard cap

Optional [admission](backpressure.md) is disabled by default. When enabled, it samples unpublished and published-without-inbox count/age, closes on high thresholds, and reopens through lower thresholds. Unknown or stale samples fail closed. A new key is checked after durable key reservation but before account locks and financial mutations; denial rolls the reservation back. Existing-key replay and conflict bypass admission.

Concurrent requests and separate instances can overshoot sampled thresholds. Retained-history scans cost work, and blocked or quarantined events can keep pressure high. These are explicit trade-offs, covered by [ADR 010](adr/010-sampled-backlog-admission.md) and [real PostgreSQL/HTTP admission checks](../src/test/java/dev/tpp/BackpressurePostgresTest.java).

## Measure the consumer before changing it

The [optimized stage diagnostic](benchmarks/phase3-profile/optimized-stage-diagnostic.json) at `66dc7c9` scheduled 4,000 arrivals at 500/s for eight seconds. It completed all 3,934 started requests and shed 66 locally, with no HTTP or ambiguous client errors. The first post-input SQL snapshot had zero unpublished events and **949 published events awaiting processing**. During the input observation, processing was 363.1/s; mean projection transaction time was 2.080 ms, offset acknowledgement 0.432 ms, and a received poll 0.106 ms.

After input, a fresh drain snapshot counted 813 remaining events; they processed in 1.331 seconds, about **610.7/s**. Mean projection transaction and offset times fell to 0.897 ms and 0.171 ms. The other 136 events progressed during inspection before that fresh drain boundary and are excluded from its rate. [Stage analysis](benchmarks/phase3-profile/optimized-stage-analysis.json) and [image/environment provenance](benchmarks/phase3-optimized-provenance.json) retain the observations.

Keep the consumer sequential and preserve its manual-offset/crash semantics. These observations support investigating shared database/HTTP contention next: transaction and offset work dominated received-poll time, and both became faster after HTTP input stopped. They do not establish a causal production bottleneck or a safe parallelism level. This diagnostic is separate from the matched comparison; process-wide timer samples and scoped SQL counts have different observation boundaries and denominators.

After all twenty-eight timed trials, the [new regression](verification/phase3-lifecycle-red-green.json) failed its intended interruption assertion against measured source `66dc7c9`. The minimal correction at `1737a27` passed two focused cases in 35.799 seconds and [separate static/dependency checks](verification/phase3-lifecycle-static.json). Reflection models admitted-start writes while stop waits on the lifecycle monitor; green recovery actually restarts the same instance and publishes an HTTP completion through Kafka with offset progress and reconciliation. This is controlled scheduling evidence, not natural JVM race reproduction. Measured images stayed fixed; the later lifecycle correction was not rebenchmarked.

Two fresh 94-test gates then failed different setup assertions: [partial-batch outstanding work](verification/phase3-clean-first-failure.json) and [shutdown outstanding work](verification/phase3-clean-second-failure.json). Both observed zero sends where their stopped-broker fixture expected more. The [corrected partial-bound fixture](verification/phase3-partial-bound-correction.json) first observes two actual accepted ACKs and zero in-flight work, then pauses the real broker. Test-only 10-second request/delivery, 30-second lease and 11.5-second coordinator windows establish six real outstanding sends and at most two next claims; focused and subsequent full-suite execution passed that case.

Close the verification chain with the [image built from that clean checkout](verification/phase3-final-build.json) and [executed runtime acceptance](verification/phase3-final-acceptance.json). The [twenty primary trials](benchmarks/phase3-comparison-summary.json) are complete. Low-contention ABBA shows a trade-off: baseline HTTP completion was 1,220–1,242/s versus optimized 1,079–1,084/s, while remaining drain fell from 95.31–110.14 seconds to 12.86–13.02 seconds and final propagation p99 from 94.08–109.37 seconds to 13.99–14.45 seconds. All twenty trials ultimately reconciled, produced paired activity for each scoped completion, and ended at zero committed-offset lag in all three partitions.

At 500 scheduled arrivals/s for thirty seconds, optimized publication kept up, but the consumer still accumulated 2,410–2,872 pending effects after input. It completed 14,351–14,466 of 15,000 scheduled arrivals, with 534–649 locally shed and no HTTP errors. Remaining drain took 4.45–4.51 seconds versus baseline 94.96–99.12 seconds. This demonstrates faster catchup, without establishing stable end-to-end capacity at 500/s. The sequential consumer decision remains unchanged.

Broker-outage trials recovered every scoped completion. Each optimized trial recorded fifteen events with another durable publication attempt; this is not a count of independently observed Kafka duplicates. Slowed-consumer recovery recreated the entire application, including producer, pool and JVM. Both optimized datasets finished before the fresh recovery observer started, so their roughly 0.22-second inspection windows supply no observed recovery throughput. The [performance analysis](phase3-performance.md) preserves these boundaries.

The separate [250/s operating-point ABBA](benchmarks/phase3-sustainable-250-summary.json) completed. Both optimized thirty-second inputs ended with no publication or projection backlog and propagation p99 of 304–314 ms; 7,427–7,433 of 7,500 arrivals completed and the rest were locally shed. Baseline remaining drains took 41.1–42.6 seconds, with propagation p99 of 40.2–41.6 seconds. This is a measured lower operating point, not a long-duration or production-capacity guarantee.

Keep the operational failure visible: after optimized trial three, a global inspection could not expand a 16 MiB PostgreSQL parallel-query shared-memory segment under the unchanged 64 MiB container limit. [Reconfirmation](benchmarks/phase3-sustainable-250/o3-post-stop-reconfirmation.json) independently found all 178,795 global events complete, zero discrepancies and caught-up offsets with the same app/configuration. Baseline trial four continued once through a separate timeline. The failed gate, interruption and observation gap remain in the summary; none of the earlier conditions was rerun or overwritten.

The original shared-source series declined strongly with chronology and retained six optimized plus three baseline dependency 503s. Its [fixture audit](benchmarks/phase3-high-fixture-order-audit.json) found 0, 1, 4 and 7 destination UUIDs below the source, changing lock order with trial position. The separately declared [controlled ABBA](benchmarks/phase3-high-controlled-summary.json) fixed all eight destinations below the source using gated harness `b11a593`, keeping both application images unchanged. B/O/O/B completion rates were 42.4/47.7/44.6/40.6 per second, with 7/3/2/10 dependency 503s, roughly 712 ms HTTP p99 and 178/183/171/169 transfer retries. All final effect and offset checks passed. This exposes contention in both conditions; limited repeats and retained failures do not establish a general causal HTTP improvement or the precise blocking cause.

[Methodology](phase3-benchmark-methodology.md) preserves each declaration and finite-arrival accounting. Persisted event timestamps are transaction-local observations, not WAL commit timestamps; a single unreplicated broker, accumulating history and one host limit capacity conclusions. The useful portfolio claim is measured faster publication/catchup with explicit HTTP, consumer and monitoring limits, supported by independently inspected durable effects.
