# Phase 3 benchmark methodology

The Phase 3 comparison uses the same instrumented harness and isolated development stack for both source versions. Historical Phase 2 results provide the investigation question; they are not the before/after control. The instrumented baseline preserves the serial relay's behavior. The optimized image is measured only after its real-dependency correctness gate passes.

## Environment isolation and image identity

Use the owned Compose project `tpp-phase3-validation`, application port 28080, database port 55434 and Kafka port 29092. Preserve the existing Phase 1 and Phase 2 projects. Record host hardware/OS, Docker CPU/memory allocation, JVM/version/flags, database and broker/client versions, effective producer/consumer settings, source revision and actual image ID. Build each source version once and select that immutable local image through a Compose override. Do not rebuild from an evolving checkout between trials.

No Maven build, integration tests, image build or unrelated experiment may run during a timed workload or drain. Existing stacks remain idle throughout both conditions. Their background monitoring and the benchmark sampler remain environmental costs. Record image swaps and trial order explicitly.

## Load models and finite client capacity

`scripts/event-benchmark.py` preserves the original closed-loop mode: each worker sends one request at a time. It reports achieved throughput and cannot establish a fixed external arrival rate.

The new `--arrival-rate` mode schedules arrivals at fixed monotonic intervals. A finite semaphore permits at most `--workers` outstanding requests; requests without a permit are counted as **locally shed** and never sent. The executor does not retain a growing queue or a list of every future. Offered, started, locally shed, successful, HTTP-rejected and ambiguous operations are separate counts. Scheduled-arrival lag has its own fixed histogram; HTTP latency measures actual request start through response/error. A delayed pacer may run behind its intended schedule; retained lag and actual arrival interval make this visible. Responses completing after the requested input interval are included in the reported completion drain and are not silently counted as completions within that interval.

Each POST uses a fresh idempotency key and is never retried by the harness. A transport failure can be ambiguous even when the server committed. Error distributions retain bounded application error codes instead of arbitrary response bodies. HTTP p50/p95/p99 are logarithmic bucket upper bounds, at most 3% bin-width error above 0.01 ms. Mean and maximum are accumulated observations. The histograms use fixed storage; sampler snapshots, workers, duration, timeouts and drain waits are bounded. Offline checks exercise capacity shedding, error accounting and stage-specific metric filtering.

Fresh double-entry funding fixtures separate every trial. Fixed-arrival fixtures fund both sides of each independent pair: scheduled requests may reorder or shed either direction, so source-only funding would cause an unintended insufficient-funds workload. The original diagnostic showing that fixture limitation is retained. Funding events are excluded from scoped user-to-user counts. A fixed-rate warmup (`--warmup-arrival-rate`) can be used before either measured load model. `--warmup-drain-timeout` explicitly requires all scoped warmup events to publish/process before measurement; this makes initial backlog comparable and preserves the warmup count/state in the report. Previous experiment backlogs must also drain before the next trial.

## Stages and timestamp meanings

Retain actuator timer snapshots separately for each operation tag, rather than aggregating claim, renewal and publication SQL into one indistinguishable number. `--metric 'name@tag=value,tag=value'` supports at most three fixed tag filters. Reports retain COUNT/TOTAL_TIME/MAX and available measurement fields. Differences of cumulative COUNT/TOTAL_TIME support interval means and rates. MAX is a rolling actuator snapshot, not an additive counter or an exact interval maximum. Do not invent percentile distributions when an endpoint does not expose them.

Baseline relay stages include claim/renew/publish/fail database transactions, Kafka enqueue, callback acknowledgement, the relay's future wait, producer creation, full batch duration and the explicit poll pause. Store timing returns after transaction completion/rollback cleanup. Kafka callback timing includes enqueue through callback observation. Callback acknowledgement and future wait describe overlapping portions of the same send; do not add them as independent costs. The same rule applies to the full batch timer and nested database/send stages.

Consumer stages include poll outcomes, projection database transaction, nested SQL work and transaction-completion remainder, post-commit projection counters, offset acknowledgement and explicit pauses. Full transaction time includes nested work and completion; those child timers must not be added again. Count `events.projection.commits` with `source=kafka,outcome=processed` for observed new durable Kafka projection effects; distinguish duplicate deliveries, replays and quarantine. Metrics are process-wide observations on an otherwise idle application, not per-fixture timestamps.

Issuance funding events are excluded from scoped user-to-user SQL counts. They can still contribute to process-wide timer/counter deltas, particularly when an outage begins before fixture funding has published. The fixture records its funding-transfer count; do not equate global stage counter denominators with scoped SQL counts.

Scoped SQL snapshots measure committed outbox/inbox/projection completeness and publication/propagation timestamp distributions. `created_at`, `published_at` and `processed_at` are transaction-local capture times persisted by committed rows, **not exact WAL commit timestamps**. Remaining commit work can make their differences understate final durable latency. Later snapshot completeness separately verifies rows became visible after commit.

Event rates use committed count deltas over database observation times. HTTP rate uses its own monotonic workload interval. Backlog drain rates use only progress after the recorded drain start, excluding progress before observation. Load-stage and drain-stage timer deltas are retained separately. Stage snapshots and resource gauges are sequential; do not treat them as one atomic observation.

The matched harness takes a fresh SQL snapshot after load-stage metric inspection and retains it as `drain.starting_events`; drain counts use this snapshot, because optimized processing may make substantial progress during inspection. The earlier original baseline diagnostic retains its original observation boundaries and is used to diagnose stages, not as a matched capacity control.

## Investigation before optimization

Start with the instrumented baseline and ordinary Phase 2 settings: relay batch 16, poll pause 100 ms, producer linger zero, buffer 4 MiB, five maximum in-flight broker requests and consumer minimum interval zero. Record a real backlog/catchup window and decompose the serial relay's elapsed time using stage counters/timers. Compare measured eligible-claim cost, renew/status cost, enqueue/ack/wait cost and polling pause. Sample runtime PostgreSQL lock/wait state, application connection pool, process CPU and JVM memory alongside publication and consumer progress. Explain missing or overlapping measurements.

A bounded Java Flight Recording may supplement that diagnostic. Store recording settings, time boundaries and actual image ID; retain the binary recording and a bounded analysis. A recording enabled at application startup includes startup activity, so its event timestamps must be related to the load/drain window. Keep profiled diagnostic observations separate from the unprofiled matched comparison. Do not infer a bottleneck solely from configured limits or source inspection.

## Matched trials and planned workloads

Use repeated counterbalanced order **baseline, optimized, optimized, baseline** for each comparison, with fresh fixtures, the same finite client capacity, warmup, duration, sampling interval, pool size and non-optimized settings. Recreate the application between trials to apply the chosen image consistently; drain prior events first. Counterbalancing reduces order/cache/history bias but does not eliminate scheduling, accumulating database history or short-run uncertainty.

Compare independent account pairs and eight clients sharing one source using closed-loop HTTP. For sustained publication, use a declared fixed arrival rate and a longer fixed input interval, retaining starting/final backlog and local shedding. Choose the rate before comparing images, based on the diagnostic question, and do not repeatedly tune it to produce a favorable result. If the harness sheds arrivals, distinguish offered input from requests that actually reached the server.

The declared comparison settings are eight workers, three seconds of warmup at 50 scheduled arrivals/s followed by complete warmup drain, and ABBA order for every case. Low- and high-contention inputs last ten seconds. Sustained input lasts thirty seconds at 500 scheduled arrivals/s, the same rate that exposed the baseline imbalance. Broker-outage and slowed-consumer inputs each last eight seconds at 500 scheduled arrivals/s without warmup; the consumer delay is 100 ms. Catchup has a 180-second deadline. Optional admission is disabled in both images so these experiments expose backlog growth instead of changing accepted workload; its rejection semantics are checked separately by the real-dependency regression.

`scripts/phase3-experiments.py` records immutable image IDs, actual ABBA order, application identities, exact load/recovery operation times, and independent broker consumer-group snapshots. Broker restoration keeps the application process unchanged. Changing the consumer budget recreates the application and is recorded as a recovery operation; progress before the observer's fresh drain snapshot is not credited to its drain rate. Each condition retains a fresh SQL fixture and the same harness source revision.

For broker-outage catchup, stop only this project's Kafka container, submit the same fixed number/rate of fresh HTTP requests, retain committed pending events, then restore that broker without restarting the application. Measure completeness, retries, duplicate effects and recovery from the observation start. Preserve the same broker volume. For a consumer bottleneck, leave publication active and set a declared positive minimum consumer interval; retain nonzero processing below publication, broker lag and SQL published-awaiting-processing. Restore the normal interval through a controlled application recreation and observe the same dataset to completion.

The outage timeline retains both the broker restoration request and health-ready observation. Catchup occurring before the recovery observer starts is excluded from its remaining-drain rate; this is not total outage recovery time. Restoring the consumer interval recreates the whole application, including relay, producer, pool and consumer. Those catchup results describe that operational recovery procedure and cannot isolate the delay setting as its sole cause.

Each comparison reports throughput, HTTP latency/error rate, propagation, durable backlog accumulation/drain, PostgreSQL contention, resource samples and reconciliation. Shared-source rejections remain failures in the report even when every committed event eventually projects. Preserve negative or noisy results.

The separate 250 scheduled arrivals/s sustained ABBA was declared once after the optimized 500/s diagnostic exposed consumer backlog. It retains thirty seconds of input, eight workers, the same drained 3-second warmup at 50/s, 180-second drain deadline, immutable images and original harness. Its files live in `benchmarks/phase3-sustainable-250`; it is an operating-point check, separate from the primary 500/s comparison, and the rate is not tuned again if unstable.

The original high-contention ABBA remains exploratory. A read-only audit of its saved fixtures found 0, 1, 4 and 7 destination UUIDs sorting below the shared source, respectively. Account order therefore differed with trial position. The additional high ABBA was declared before execution and runs only after the original twenty primary and four 250/s trials. It fixes all eight destinations below the source, retains the same images, eight workers, ten-second closed-loop input, drained 3-second warmup at 50/s and 180-second drain deadline, and writes to `benchmarks/phase3-high-controlled`.

That optional fixture control changes only the leading UUID nibble: `f` for the shared source and `0` for each destination. The remaining 124 namespace-derived bits, UUID version/variant, independent low pairs and issuance account stay unchanged. PostgreSQL compares UUID bytes, so this construction guarantees the declared order while each fixture remains fresh. It changes no financial operation or database schema. The default fixture remains unchanged. The extension is gated and recorded under a new immutable harness revision; the original harness stays frozen through its twenty-four trials. Possible interaction between account locks and projection foreign-key locks is a hypothesis, not a demonstrated cause of the original decline.

The actual 250/s attempt stopped after O3's scoped SQL and committed-offset gates because global reconciliation queries exhausted PostgreSQL's 64 MiB container shared-memory area. The original failed timeline remains intact. Independent reconfirmation observed complete scoped/global work with the same app and resource configuration; original planned B4 continued once in a separate directory with verified source-66 core harness files. No measured condition was rerun or overwritten. The combined summary explicitly records that interruption, reconfirmation, gap and continuation. It does not reclassify the operational endpoint failure as a successful uninterrupted run.

## Correctness and interpretation

Every sampled scoped snapshot requires one outbox row per completed transfer, one projection per inbox row and two account activity rows per inbox row. Authoritative ledger/balance reconciliation must pass before/after each workload. Catchup requires all scoped events published and processed. Independent broker group snapshots corroborate lag and offsets; their timestamps may differ from SQL samples. A separate bounded final gate requires committed offsets to equal broker log end with zero lag in all three partitions. SQL effects alone do not prove offset acknowledgement, and the consumer's fetch-position lag gauge cannot substitute for this broker check.

These benchmarks complement the full real PostgreSQL/Kafka failure regression; they do not replace it. A single host and single broker do not model infrastructure failover. Finite memory does not imply finite durable storage. Sustainable capacity needs a stable backlog over a meaningful fixed-input observation interval; a fast backlog drain or brief burst alone does not establish it. Report uncertainty and remaining limits rather than claiming production readiness.
