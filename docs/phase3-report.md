# Phase 3 engineering report

Phase 3 replaces the measured serial publication bottleneck with bounded asynchronous publication and fenced batch settlement. PostgreSQL remains authoritative for financial state and event identity. The existing consumer still commits each durable inbox/projection outcome before acknowledging its Kafka offset.

Completed validation on 2026-10-12: final implementation `2c859cb` passed fresh-checkout `clean verify` and final Docker acceptance. All 94 tests passed, including 34 unit and 60 real-dependency integration cases, with zero failures/errors/skips and zero SpotBugs bugs/errors. All 28 measured trials completed. Earlier failed attempts, the original high-contention confound and the 250/s operational interruption remain visible.

## Implemented

The relay now renews a bounded claim batch in one transaction, submits independent Kafka records asynchronously, and persists their individual results in one bounded transaction. Callback state is keyed by event ID and claim token, validates the configured topic and nonnegative Kafka position, and freezes before settlement. Callbacks perform no SQL. Successful Kafka acknowledgement and committed PostgreSQL publication are separate observations.

A semaphore bounds actual outstanding sends across batch deadlines: freezing an unresolved batch does not release permits for sends whose callbacks have not finished. One coordinator operates per relay instance. A fully committed full batch immediately attempts more work; idle, partial and failed batches retain the configured pause, and durable retry scheduling remains capped and jittered. Producer linger, buffer size and broker request limits remain unchanged. Shutdown cancels coordinator work and preserves unresolved claims for lease recovery. A subsequent minimal lifecycle correction reasserts stopped flags and recaptures the current worker/coordinator under the shared start/producer monitor, preventing an already admitted start from installing a worker missed by stop's earlier capture.

Optional sampled backlog admission, disabled by default, checks unpublished and published-without-inbox counts and ages. Hysteresis stabilizes reopening; enabled admission rejects unknown or stale evidence. The check follows durable existing-key arbitration and precedes financial mutations. A denied new request rolls back its key reservation and returns HTTP 503 with `Retry-After: 1`; previous results still replay and payload conflicts still return HTTP 409. Thresholds are local, sampled operating signals and can be overshot by concurrent work. They are not a shared hard queue or disk-capacity reservation.

Stage timers distinguish relay claim/renew/settlement, Kafka enqueue/acknowledgement, consumer transaction/work/completion, and offset acknowledgement. Backlog gauges retain real cached evidence with exposed age and report unknown initial values. The finite-capacity benchmark harness separates offered arrivals, local shedding, successful responses, HTTP errors and ambiguous transport outcomes. See [relay design](outbox.md), [admission policy](backpressure.md), and [ADRs 009](adr/009-bounded-batch-relay.md) and [010](adr/010-sampled-backlog-admission.md).

## Bottleneck Diagnosis

The instrumented serial baseline is commit `cba44277524cb6b10c688a225afee9d396dfd135`, rather than the historical Phase 2 measurements. In a real backlog drain, 191 observed relay cycles spent 19.330 seconds pausing and 6.316 seconds doing batch work: the configured pause represented 75.4% of those intervals. Claim, per-event renewal and per-event publication transactions consumed 4.785 seconds, 75.8% of active batch work. Serial Kafka future waiting consumed 1.211 seconds, 19.2%; callback timing overlaps that wait and cannot be added again. This justified removing productive full-batch pauses and per-event database round trips, with asynchronous sends preserving a finite outstanding bound. See the [stage analysis](benchmarks/phase3-baseline-stage-analysis.json).

A recovered and validated sixty-second JFR recording separately corroborated relay sleeping: the filtered catchup window contained 133 sleep events totaling 13.45 seconds. Its requested destination dump failed; the completed repository chunk was recovered and the failure retained. Only ten execution samples per relay/consumer thread were available in that window, so no precise CPU hotspot is inferred. The [recording evidence](phase3-performance.md#flight-recording-corroboration) remains separate from unprofiled comparisons.

After relay optimization, a separate eight-second diagnostic completed 3,934 of 4,000 offered requests, shed 66 locally and reported no HTTP errors. All 4,084 scoped events including warmup were published at input end, but 949 awaited projection. Consumer projection transactions averaged 2.080 ms during input and 0.897 ms after input stopped; offset acknowledgement averaged 0.432 and 0.171 ms respectively. Processing reached 363.1/s during concurrent input, versus about 611/s over a short subsequent drain. Database work dominated measured consumer costs, and the difference suggests shared-resource contention without isolating its exact cause. The sequential consumer and manual per-record offsets are retained; its next optimization requires evidence under concurrent input. See the [optimized stage analysis](benchmarks/phase3-profile/optimized-stage-analysis.json).

## Performance

The comparison uses immutable baseline and optimized commit `66dc7c9cbcdd312f9df5ed427520bc398d7696a0` images, the same harness, fresh fixtures and JVMs, eight clients, and baseline/optimized/optimized/baseline order for each workload. No tests or builds run during timed load or drain. The host is an Apple M2 Max with 12 logical CPUs and 32 GiB RAM, macOS 26.7.1; Docker's VM reports 13 CPUs and 7.667 GiB. Java 21, PostgreSQL 17.11, Kafka 4.3.1, relay batch 16, pool 16 and admission disabled are recorded in [provenance](benchmarks/phase3-baseline-provenance.json). This is one local host with one unreplicated broker.

The completed low-contention comparison demonstrates faster event processing with an HTTP cost. Baseline HTTP throughput was 1,220–1,242/s; optimized was 1,079–1,084/s, with no errors. HTTP p99 histogram bounds increased from 14.0–16.7 ms to 19.3–19.9 ms. Publication during the SQL observation interval increased from about 68.8/s to 1,054–1,059/s. Remaining projection drain completed in 12.9–13.0 seconds, versus 95.3–110.1 seconds for the baseline publication/processing drain. Final propagation p99 decreased from 94.1–109.4 seconds to 14.0–14.5 seconds. These conditions created different numbers of successful transfers; their drain rates and times do not establish sustained capacity. The new limiting stage is the consumer during concurrent HTTP work.

At 500 scheduled arrivals/s for thirty seconds, optimized publication matched observed committed creation at 474–478/s, versus baseline publication of 92–110/s. Optimized projection reached 383–395/s and still accumulated 2,410–2,872 published events awaiting processing; baseline accumulated 11,476–11,850 unpublished events. Optimized propagation p99 was 7.37–8.95 seconds, versus 93.97–98.00 seconds, but 500/s remains an unstable end-to-end operating point. All sent requests succeeded. Of 15,000 offered arrivals per trial, optimized shed 534/649 locally versus baseline 191/354. Faster publication has shifted the limiting stage without making offered input sustainable.

The original high-contention series is retained as negative, exploratory evidence. In chronological ABBA order, HTTP throughput was 348.8, 172.8, 82.2 and 45.8/s. The last optimized and last baseline trials returned six and three `DEPENDENCY_UNAVAILABLE` HTTP 503 responses. ## Correctness

The V1–V3 schema and financial transaction boundary are retained: balanced immutable postings, conserved materialized balances, durable transfer idempotency, and one immutable event for every completed transfer. Kafka remains at-least-once transport. A callback cannot publish an unsent record or a different claim generation. Each settlement row independently checks event identity, token, `CLAIMED` status and a live database lease. Applied IDs and success counters are used only after transaction completion.

If settlement fails after Kafka acceptance, all status updates roll back and claims become eligible after lease expiry. Republishing uses the same event identity; the durable inbox suppresses repeated projection effects. Publication order can change across workers, retries and callback completion. Kafka partition order cannot repair upstream races. The implemented activity projection depends on immutable event identity and additive effects, rather than strict publication order.

Admission refuses new work before a financial commit and rolls back temporary reservations, while preserving replay/conflict behavior. The consumer's atomic inbox/projection, durable quarantine, audited replay and offset-after-durable-outcome rules remain unchanged. Observed benchmark datasets reconcile ledger and paired activity effects after drain; finite schedules and source review complement rather than replace failure testing.

## Limitations

These short repeated trials demonstrate local behavior, with two runs per condition, finite client capacity, retained historical rows and coarse sequential samplers. Counterbalancing reduces but does not remove order/history bias. The original high-contention account-order difference prevents a clean causal comparison. The original baseline diagnostic's ten insufficient-funds responses came from source-only fixture funding under reordered/shed reverse requests; that failure is retained and both sides are funded for matched fixed-arrival trials.

Faster publication increases competition with HTTP and downstream processing; lower propagation delay does not imply higher HTTP throughput. A drain after input stops is not sustainable throughput. Consumer lag must be checked independently against committed broker offsets, because local fetched-position lag can be zero before final durable projection or acknowledgement.

Lease fencing protects publication evidence, while inbox uniqueness protects projection effects; it does not eliminate Kafka duplicates. A network error during COMMIT can have an unknown server outcome. Batch settlement increases the number of acknowledged records affected by one database failure, and preserved leases/identities make that recovery safe. Producer construction can hold the lifecycle monitor during OS/JVM DNS resolution; tested shutdown timing is not a universal bound for resolver stalls.

Admission is disabled by default, can overshoot when enabled, scans retained history, and does not measure disk free space. PostgreSQL/Kafka history, deduplication and replay evidence remain unbounded over deployment lifetime. The observed global reconciliation shared-memory failure is an operational resource limit, even though later unchanged-state inspection found all effects complete. Replication, storage exhaustion, long-duration operating capacity and production readiness are not established.

## Resume Candidates

- Implemented bounded asynchronous Kafka publication with immutable per-event callback state, lease-generation fencing and atomic PostgreSQL batch settlement, preserving at-least-once recovery and idempotent projection effects.
- Diagnosed serial polling/SQL overhead and reduced local independent-pair propagation p99 from 94–109 seconds to 14–14.5 seconds in counterbalanced trials, documenting the HTTP throughput cost.
- Added sampled admission before financial mutation and verified financial/event invariants with 94 automated cases, including 60 real-dependency integration tests and actual batch-failure/shutdown recovery.

## Phase 4

1. **Measure and improve consumer throughput under concurrent input.** Isolate projection transaction/commit and shared-resource costs, then compare bounded group/partition scaling or targeted SQL changes. Retain per-partition offset, rebalance, inbox and quarantine correctness gates.
2. **Design retention and archive with a deduplication horizon.** Bound outbox/inbox/projection/audit storage and reconciliation cost while preserving immutable financial evidence, replay safety and rebuild ability. Add real volume-capacity signals before storage exhaustion.
3. **Strengthen capacity experiments and operational limits.** Repeat longer controlled-history trials, investigate the shared-account chronological degradation, and test measured admission thresholds under multiple application instances and resource budgets. Distinguish sampled best-effort refusal from any future durable hard-cap guarantee.
